SOCIAL NETWORK - LAB 5 (PostgreSQL persistence with JDBC)
=========================================================

Lab 5 continues the project from Lab 4. The functionality is unchanged (add/remove user, add/remove
friend, number of communities, most sociable community); what changes is that the data can now be
kept in a PostgreSQL database, and the id of a new user is generated by the storage, not by the
service. When a user is added, the application shows the id received from the database.
The type of persistence (DATABASE, FILE or MEMORY) is chosen only in config.properties.

Only the parameters of the selected type are required.


3. THE DATABASE
---------------
users(id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      username VARCHAR NOT NULL UNIQUE, email VARCHAR NOT NULL UNIQUE, password VARCHAR NOT NULL)
friendships(id1 BIGINT, id2 BIGINT, friends_from TIMESTAMP NOT NULL,
            PRIMARY KEY (id1, id2), CHECK (id1 < id2),
            FOREIGN KEY (id1) REFERENCES users(id) ON DELETE CASCADE,
            FOREIGN KEY (id2) REFERENCES users(id) ON DELETE CASCADE)

Columns of users: the users keep the fields used since Lab 2 (username, email, password) instead of
first_name / last_name, so the table has the same data as the files and the other repositories.
The id is generated by the database (GENERATED ALWAYS AS IDENTITY), as required. username and email
are UNIQUE, so the database also enforces the uniqueness rule checked by UserService.

friendships: the primary key (id1, id2) allows a pair of users to be friends only once;
CHECK (id1 < id2) matches Friendship.normalize, which always stores the smaller id first;
friends_from (TIMESTAMP) maps to LocalDateTime.

Deleting a user - ON DELETE CASCADE and deletion in the service (both are used):
  - UserService.beforeRemove deletes the user's friendships before the user is deleted. This is
    needed because the same service also works with MEMORY and FILE, where there is no database to
    do it; the business rule stays in the service, independent of the storage.
  - The foreign keys with ON DELETE CASCADE guarantee consistency inside the database itself, even
    when a user is deleted outside the application (for example in pgAdmin).
  In the application the service deletes the friendships first, so the cascade finds nothing left
  to delete; it is a safety net, not a second copy of the logic.


4. JDBC REPOSITORIES
--------------------
UserDbRepository and FriendshipDbRepository implement UserRepository / FriendshipRepository (so
Repository<ID,E>) and extend AbstractDbRepository<ID,E>, which holds what both need: the validator,
the connection parameters received from the factory (db.url, db.user, db.password), connect() and
requireNonNull(...). The repositories keep no entities in memory: every operation reads from or
writes to the database, so changes made in pgAdmin are seen by the application.

- Connections: every operation opens its own connection with
  DriverManager.getConnection(url, user, password); Connection, PreparedStatement and ResultSet are
  opened in try-with-resources, so they are closed even when an exception is thrown.
- SQL: all queries use PreparedStatement with ? parameters (setString, setLong, setTimestamp); values
  are never concatenated into the SQL text. The only fixed text built into the SQL is the list of
  column names, written as constants in the code.
- Generated id: UserDbRepository.save prepares the INSERT with Statement.RETURN_GENERATED_KEYS, runs
  executeUpdate() and reads the id with getGeneratedKeys(); the id is set on the user, which is
  returned and shown by the UI. Without it the caller would not know the id of the saved user.
  Friendships have no generated id: their id is the pair of user ids.
- Reading rows: a private helper (extractUser / extractFriendship) converts one row into an entity,
  so the mapping is written once.
- findAll(Predicate) is inherited unchanged: it calls findAll() (the SELECT) and filters in Java.
  [CHECK: if you kept the SQL overrides of findByUsername / findByEmail in UserDbRepository:]
  UserDbRepository overrides findByUsername / findByEmail with a single
  "SELECT ... WHERE username = ?" query instead of the default wrapper that filters all users in
  Java; the interface did not change, only the database implementation is more efficient.


5. THE REPOSITORY CONTRACT (same for MEMORY, FILE, DATABASE)
------------------------------------------------------------
- null argument (entity or id) -> IllegalArgumentException;
- save and update validate the entity before storing it (Validator received from the factory);
- save returns the saved entity (for users, with its id set by the storage);
- delete returns the deleted entity, or an empty Optional if none had that id
  (the database repositories read the entity first, then delete it);
- update returns an empty Optional if the entity was updated, and the entity itself if no entity
  had its id. In the database this is decided by executeUpdate(), which returns the number of
  changed rows: 0 means no row has that id, so no SELECT is needed first.
The update contract was changed in InMemoryRepository and AbstractFileRepository too (in Lab 4 it
returned the old entity), so the three storages can replace each other (LSP); the Javadoc of
Repository.update was changed accordingly.


6. EXCEPTIONS
-------------
Every SQLException is wrapped in a RepositoryException (with the SQLException as cause) by
SqlErrors.wrap, which chooses a specific message from the standard SQL state of the error:
  08xxx   server not reachable    "The database server is not reachable. Check that PostgreSQL is running..."
  28P01   wrong password          "The database rejected the user or password..."
  3D000   database missing        "The database in db.url does not exist."
  42P01   table missing           "A table is missing in the database. Run schema.sql first."
  23505   unique violation        "Could not ...: this entry already exists."
  23503   foreign key violation   "Could not ...: it refers to a user that does not exist."
  23514   check violation         "Could not ...: the data breaks a database rule."
ConsoleUI catches RepositoryException and prints the message, so a stopped server or a violated
constraint produces a specific message in the UI, without a stack trace, without empty catch blocks
and without catch (Exception e). Business rules (unique username/email, both users exist, no
duplicate friendship) are still checked first in the services, with their own messages; the
database constraints are the safety net.
The other exception rules from the previous labs still apply: own unchecked exceptions, exception
chaining, exceptions caught only in ConsoleUI and Main.


7. SQL INJECTION
----------------
Because every value is passed as a PreparedStatement parameter, the driver sends it separately from
the SQL text: a value such as '); DROP TABLE users; -- is stored as ordinary text and never executed.

8. HOW THE FACTORY WORKS (Map + Supplier, no switch)
----------------------------------------------------
RepositoryFactory is the only class that knows the concrete repository classes.
- Its constructor reads src/main/resources/config.properties with java.util.Properties
  (try-with-resources) and converts repository.type into RepositoryType { MEMORY, FILE, DATABASE }.
- createUserRepository(validator) and createFriendshipRepository(validator) each have a
  Map<RepositoryType, Supplier<...Repository>> with one supplier per type, e.g.
    MEMORY   -> () -> new InMemoryUserRepository(validator)
    FILE     -> () -> new UserFileRepository(validator, getRequired("file.users"))
    DATABASE -> () -> new UserDbRepository(validator, getRequired("db.url"),
                                           getRequired("db.user"), getRequired("db.password"))
  Only the supplier of the configured type is called, so only that repository is created and only
  its parameters are read. The suppliers capture the validator received by the method.
- Both repositories are created for the same type. A missing or unknown value produces a
  ConfigurationException with a clear message.
- Main, the services and the UI use only the interfaces: switching between DATABASE, FILE and
  MEMORY is done only in config.properties, without changing any Java class.

In every pipeline, filter/map/sorted/distinct/mapToInt are intermediate operations (lazy, they
only describe the processing) and collect/count/max/findFirst/anyMatch/forEach are terminal
operations (they start the processing and produce the result or perform the action).
Results are built with terminal operations (collect, count, max, findFirst), never by adding to
an outside list from forEach. The functions passed to filter and map have no side effects; changes
(deleting, printing, loading a line, the DFS recursion) happen only in forEach.


10. LAB 4 - FUNCTIONAL INTERFACES, LAMBDAS AND METHOD REFERENCES
----------------------------------------------------------------
Functional interfaces used:
  Validator<T>     own interface, @FunctionalInterface; implemented by the validator classes and by
                   lambdas; combined with the default method andThen(Validator<T> other).
  Predicate<T>     search criteria for findAll(Predicate) (UserCriteria, FriendshipCriteria), filter.
  Supplier<T>      RepositoryFactory: one Supplier per RepositoryType creates the repository.
  Function<T,R>    map(...), Optional.map(...), Comparator.comparing(...), Collectors.toMap(...).
  ToIntFunction /  Comparator.comparingInt(...), mapToInt(...), mapToLong(...).
  ToLongFunction
  Comparator<T>    sorted(...), max(...), built with Comparator.comparing / comparingInt.
  Consumer<T>      forEach(...).

Validation with a lambda (no new class, UserValidator unchanged):
  In Main, new UserValidator().andThen(user -> { ... "Username must start with a letter." ... })
  is passed to the factory. andThen returns a validator that applies UserValidator first and the
  lambda rule second.

Method references - all four kinds:
  static method                          Long::parseLong, Objects::nonNull
  instance method of a particular object System.out::println (ConsoleUI),
                                         friendshipRepository::delete (UserService.beforeRemove),
                                         userService::findOne, this::createEntityAsString
  instance method of an arbitrary object User::getUsername, Friendship::getId, Entity::getId,
                                         Optional::stream, Optional::isEmpty
  constructor                            HashSet::new / ArrayList::new
Lambdas that only call one method with the same arguments are written as method references;
lambdas remain where they add an argument or contain logic (for example the factory suppliers,
which capture the validator).


11. SEARCH CRITERIA (findAll(Predicate))
----------------------------------------
Repository<ID,E> has the default method List<E> findAll(Predicate<E> filter), the general search
method; it works for every storage, including the database, because it is built on findAll().
Criteria are static methods returning predicates (package criteria):
  UserCriteria.hasUsername(username), UserCriteria.hasEmail(email), ...
  FriendshipCriteria.involves(userId)
They are combined with and / or / negate / Predicate.not. Example in running code:
  FriendshipService.removeFriendship checks that two users are friends with
  FriendshipCriteria.involves(user1).and(FriendshipCriteria.involves(user2)).

UserRepository keeps findByUsername / findByEmail as one-line default wrappers:
  findAll(UserCriteria.hasUsername(username)).stream().findFirst()
They contain no search logic of their own and only shorten the most frequent lookups. A new kind
of search is a new criterion in UserCriteria (or a lambda combined with existing ones), never a new
repository method.


12. FILE REPOSITORIES: TEMPLATE METHOD (kept) vs. Function (composition)
------------------------------------------------------------------------
Choice: Template Method is kept. AbstractFileRepository<ID,E> extends InMemoryRepository<ID,E> and
contains all reading/writing code; UserFileRepository and FriendshipFileRepository only implement
extractEntity(String line) and createEntityAsString(E entity).

Reading: Files.lines(path) inside a try-with-resources (the stream keeps the file open), collected
into a list; IntStream.range(0, lines.size()) keeps the line numbers, so corrupt lines are still
reported as "line N skipped". Loaded entities are stored with super.save(...) (validated, file not
rewritten while reading). Writing: Files.write(path, lines), where lines come from a stream over the
entities mapped with this::createEntityAsString. IOException and UncheckedIOException are wrapped in
RepositoryException.

Why Template Method:
  + the subclasses already exist, each with a clear name and the file format in one place;
  + each subclass also adds entity-specific behaviour (UserFileRepository assigns new ids in save),
    which fits naturally in a subclass;
  + it keeps the hierarchy InMemoryRepository -> AbstractFileRepository required in Lab 3.
  - it uses inheritance, and the constructor calls overridable methods (extractEntity); this is safe
    because the subclasses' implementations use only static constants.
The same idea is used for the database: AbstractDbRepository holds the shared connection code and
the subclasses only write the SQL for their table.


13. OPTIONAL
------------
Repository returns Optional<E> (findOne, delete, update) instead of null. The absence of a value is
part of the method's type, so callers cannot forget it, and they handle it with orElseThrow, orElse,
map or ifPresent instead of null checks. All implementations (memory, file, database) and the Javadoc
are consistent with this.
Optional is also used for the results of max, min, findFirst (e.g. the most sociable community,
the next id, lookups by username). Values are extracted with orElseThrow / orElse / map, never with
get() without a check. Optional is used only as a return type, not for fields or parameters.


14. SORTING
-----------
Sorting uses only Comparator.comparing / comparingInt / reversed, never a hand-written compare:
  - friends and community members sorted by username: Comparator.comparing(User::getUsername);
  - the most sociable community: max(Comparator.comparingInt(node -> longestPathFrom(...))).
In the database, findAll() returns the rows ordered by id (ORDER BY id).


15. LOOPS KEPT AND WHY
----------------------
- ConsoleUI.run: while (true) reads user commands until "exit". It does not iterate over a
  collection, so it is not covered by the "no loops over collections" rule, and a stream would not
  make it clearer.
- CommunityService.longestPathFrom keeps a for loop: it is a backtracking algorithm that adds a node
  to the current path, explores all neighbours and removes the node again; writing the recursion
  with streams makes the undo step harder to follow.
- UserDbRepository.findAll / FriendshipDbRepository.findAll: while (rs.next()) is the standard way
  to read a JDBC ResultSet, which is not a collection and has no stream API.


16. MISSING FILE, CORRUPT LINES, VALIDATION (FILE mode, unchanged)
------------------------------------------------------------------
Missing file: the repository starts empty; the file is created at the first save.
Corrupt line: reported with file name, line number and reason, then skipped
  (e.g. "Warning: data/utilizatori_corupt.txt, line 2 skipped: invalid user id 'abc'").
  The per-line catch is narrow (RepositoryException, ValidationException, DuplicateEntityException
  for that one line). After the next change the file is rewritten from memory, so skipped lines
  disappear: keep a copy of the *_corupt.txt files to repeat the demo.
Consistency: friendships whose users do not exist are removed at startup
  (FriendshipService.removeFriendshipsOfMissingUsers, reported by the UI); while running, a
  friendship needs two existing users and removing a user removes their friendships.
Validation: entity data is validated in the repository (every save/update and every loaded line),
  with the validator received from the factory; rules that need other data (uniqueness, users
  existing) are in the services (checkBeforeAdd hooks).


17. DESIGN PRINCIPLES AND PATTERNS
----------------------------------
SRP - entities hold data, validators check data, criteria describe searches, repositories store,
      SqlErrors translates database errors, services apply business rules, ConsoleUI talks to the
      user, the factory chooses repositories.
OCP - the database persistence was added as new classes (db package) and one map entry per
      repository in the factory; services, UI and Main did not change. A new validation rule is a
      lambda combined with andThen; a new search is a new criterion or a combination of predicates.
LSP - memory, file and database repositories can replace each other wherever a UserRepository /
      FriendshipRepository is expected, with the same Javadoc contract (see section 5).
DIP - services depend on Repository / UserRepository / FriendshipRepository and Validator, never on
      concrete classes; the factory creates the objects and they are injected through constructors.
Patterns:
  Factory          RepositoryFactory (Map of Suppliers instead of switch).
  Template Method  AbstractFileRepository, AbstractDbRepository (shared code, subclasses give the
                   format / SQL of their entity) and AbstractService (add/remove steps, hooks
                   checkBeforeAdd / beforeRemove).
  Strategy         Validator<T>; strategies are composable with andThen and can be lambdas.
  Decorator        Validator.andThen wraps a validator with another one; the readers used by
                   Files.lines are buffered (decorated) streams.
  Repository       storage hidden behind Repository<ID,E>.
  Layered architecture: UI -> service -> repository -> model.

--------------------

  adduser <username> <email> <password>     (or just "adduser" to type each field on its own line)
  removeuser <id | username>
  addfriend <id1 | username1> <id2 | username2>
  removefriend <id1 | username1> <id2 | username2>

Demo:

  - adduser shows the id generated by the database;
